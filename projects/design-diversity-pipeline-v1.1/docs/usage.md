# 操作方式：从新对话到一批可用网站

## 1. 给Claude哪些文件

将本包提供给Claude，先加载prompts/system-prompt.md，再用prompts/kickoff.md发送具体任务。真正的system槽不可用时作为首条项目约定，不声称能覆盖客户端系统限制。

填写examples/task-batch.json：品类、业务分支、用户路径、页面范围、目录、candidate_pool_target、delivery_target、预算和授权。默认query_only＋reference_board；不会开发业务页面。

三类常见任务：

| 任务 | 设置 | 输出 |
|---|---|---|
| 学知识与配方 | query_only＋reference_board | 候选表、配方、参考、Query与Prompt |
| 先看方向预览 | query_only＋rendered_preview，preview_render=true | 上述内容＋有限预览，整站不开发 |
| 完整制作 | build，build=true | 先交付指令，再制作与四张检查单 |

## 2. 第一阶段：固定业务

确认用户、目标、数据、状态、无障碍目标与页面清单。例如商品列表＋详情＋购物袋；不要把结账作为风格探索时临时加出来。不同业务分支分批。

业务不明确时问关键问题；字体来源、可逆目录选择等可记录默认值。使用现有知识，不默认重抓所有站点。

## 3. 第二阶段：学习参考，写候选配方

设计参考与交付图片分开找。每个候选填写recipe-template：方向、页面组织、依据、素材条件、为何值得做、与最近候选的区别。

先写全批次方向表，再细化单方向。12选3只是一个例子；若目标10个，可按预算建立更大的候选池，或分轮补足。不要在模糊名称上直接选数量。

## 4. 第三阶段：两条线筛选

质量线先排除业务、布局、字体、素材条件不成立的方向；差异线再比较结构/风格/图像/交互。素材未齐的候选可条件性保留，但不计完整交付就绪。

没有校准数据时先用具体理由与0–3档，不套任意固定百分比。每次选择同时看最接近的方向，不只看平均差异。

## 5. 第四阶段：预览与身份锁

已授权渲染预览时先做桌面首屏＋代表区域，必要时手机首屏。统一业务内容和视口，注明素材限制；不宣称预览已验证整站行为。

每个入选方向锁3–5个特点及相关字段范围。比如衬线标题、暖底色、细线分隔、图文交替。给下一阶段模型明确“不能修没什么”。

## 6. 第五阶段：交付制作说明

每方向交付简短Query全文、完整Prompt、配方、resolved、素材与报告。多页站点先列总Prompt和页面Prompt的执行入口；若页面Prompt要脱离总包单独执行，展开必需公共规则。

query_only到此停止；build继续修改授权目录。共享业务层、无样式交互能力和数据模型，不强制各方向共享相同页面布局或视觉组件。

## 7. 第六阶段：稳定实现

按Foundation→核心组件→核心体验→整站。

- Foundation阶段先确认字体真正可用、字重与字符覆盖、布局尺寸和身份关系。
- 组件阶段测按钮长文本、价格、错误、禁用和焦点。
- 核心体验阶段测关键任务链和异步状态。
- 整站阶段测同方向各路由一致性和响应式。

每个阶段处理当前高影响问题，不跑无关检查。详见generation-stability.md。

## 8. 第七阶段：四张检查单

功能完整 → 单页质量 → 同站一致 → 方向差异。构建10页时对45对做配置筛查，视觉优先最近邻，但未审查的对不宣称通过。只有一个页面时，同站检查写not_applicable及原因。

问题回到所属层：知识错误改claim，配方冲突改源配置，字体/图片缺失改素材，代码问题修实现。每问题两轮后根因复盘。保留已合格方向，不全批次重写。

## 可直接发的后续操作

“只交付十个网站配方、短Query和完整制作说明，暂不实现。”

“我授权为候选做桌面首屏和手机首屏预览，选定方向前不开发整站。”

“按已选配方实现三个方向，共享业务逻辑，各方向保留自己的布局与字体身份。”

“只修字体加载和1024布局溢出，锁定现有视觉身份，输出补丁与回归结果。”

## 包内验证

python3 scripts/validate.py

只验证资料包，不是真实网页检测。任务示例含占位路径，必须由使用者填写；未填写不得当成可执行工作目录。
