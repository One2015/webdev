# 参考图到交互原型

## 选择执行范围

- 制作或调整原型：执行分析、实现、验证闭环。
- 只要求拆图或基础规范：输出 Visual Contract 和组件/状态清单后结束，不写产品代码。
- 只要求审查：输出有证据的差异报告，不修改产品；明确要求修复时再修改。
- 已有参考图直接开始分析，仅补搜具体缺口。只有用户要求批量检索/覆盖审查时才运行完整检索 pipeline。

先读取项目现有规范、技术栈和组件，识别用户任务、目标端、页面范围、必要交互及素材。可从上下文判断的内容不重复询问；只有关键缺口阻塞执行时提问。缺少可查看的图时不能伪称完成视觉分析。用户明确要求优先于本 skill 默认值。

## 1. 将参考变成视觉约定

实际查看参考图。每个页面、每种端形态默认选一张 Primary、最多两张 Secondary：主图控制整体布局、层级、密度和节奏；次图只负责指定局部，不能改变全局风格。跨页面保持统一 Foundation。

记录 COPY（保留的比例、对齐与节奏）、ADAPT（业务内容、数据和跨端行为）、IGNORE（无关内容和未指定使用的素材）。替换文案与图片时维持行数、占位比例和视觉重量。

在实现前输出简短 Visual Contract，至少包括：

- 参考角色和 scope、适配理由、目标平台及 viewport。
- 布局/间距、文字、组件尺寸、表面、颜色角色、密度的关键 tokens。
- 关键值的单位、来源、observed/inferred/chosen 及 confidence。截图物理像素不直接当逻辑尺寸。
- P0：整体比例、间距、层级、密度；P1：组件尺寸、边框、圆角、颜色；P2：装饰细节。按任务调整排序和容差，不硬套示例数值。
- 本页组件、必要状态、核心交互、响应式规则、未知项及验收条件。

需要字段模板、示例或完整检索流程时读取 [pipeline-and-contract.md](references/pipeline-and-contract.md)。信息足够且用户要求实现时，输出约定后直接继续。

## 2. 补齐所需规则并实现

优先复用项目 tokens 与组件。先整体骨架，再字体与密度，再组件和真实任务流。不要默认套 12 栏或用新库重写已有系统。只覆盖本页实际需要的组件和状态。

DS 信息不足时读取 [design-system.md](references/design-system.md)：按具体缺口检索官方资料，记录 applicable_context、anti_context、selection_reason、来源与版本。仅注入相关片段，将其映射回项目 tokens。未提供的 Mobbin/SD/PA 连接不能假定可用；来源不可访问则明确标记。

单图无法证明交互或断点，推导部分标记 ADAPT。区分手机 Web 和原生实现。将模拟数据和未实现的后端能力明确标记，核心操作应能在约定范围内跑通。

## 3. 截图、比较、定向修复

实现后读取 [multi-platform-review.md](references/multi-platform-review.md) 的多端检查和截图修复规则。使用当前环境可用的浏览器、模拟器或截图工具；本 skill 不自带连接器，也不依赖其他自定义 skill。

统一 viewport、缩放/DPR、裁切、滚动位置、主题、语言、数据、状态，等待字体和图片稳定。对照主图与 contract，记录 PASS/FAIL/UNVERIFIED，先修 P0，再修 P1。

每条差异写“区域 → 预期 → 实际 → 证据 → 原因 → 修改 → 回归检查”。每轮聚焦少量高影响问题，复查修改后的截图及受影响交互，保留已通过区域。不要把每次修复变成整页重新设计，也不要伪造相似度百分比。

连续两轮无改善时检查分析、字体、素材或环境根因，再采取有依据的下一步；存在无法解决的阻塞时报告具体缺口。达到预算不代表通过。没有实际截图时标记视觉验收 UNVERIFIED，完成仍可进行的实现与检查。

## 交付与反馈

按任务范围交付 contract/分析报告，或可运行原型、实际截图、验收记录和剩余差异。通过条件是 P0 达标、重要 P1 已修复或由用户明确接受、核心任务及声明支持的平台与必要状态已检查。

在项目内保存有助于后续工作的参考 ID、context、tokens、差异原因和用户取舍。不要因一次设计选择自动改写个人 skill；可复用规则需要后续有依据的更新。普通原型任务不自动扩展为部署、外部发布或全套 DS 建设。
